5. CENTRALIZED FEATURE-GATE SYSTEM

Implement a central configuration system with exactly five primary operating profiles.

The developer selects one profile.

Every subsystem must determine its permitted behavior from this central authority.

Suggested configuration:

[GUNPIRE]
profile = TEST_SINGLE_SHIP

[SAFETY]
enforce_cargo_empty = true
preserve_original_behavior = true
preserve_trader_progression = true
enforce_reservations = true
safe_restoration = true

[DIAGNOSTICS]
enabled = true
verbosity = DEBUG

Safety requirements are mandatory invariants, not optional features.

Changing profile must never bypass safety protections.

Profile 1: TEST_SINGLE_SHIP

Purpose: Validate a complete production delivery lifecycle with one specifically authorized ship.

Enable:

- Core runtime
- Configuration
- One-ship enrollment
- Cargo eligibility
- Original assignment snapshot
- Safe takeover
- Demand discovery
- Supplier discovery
- Minimum required reservations
- One real purchase
- One real construction delivery
- Safe restoration
- Targeted diagnostics

Disable:

- Fleet-wide takeover
- Multiple simultaneous controlled ships
- Advanced fleet distribution
- Multi-site optimization
- Nonessential UI workflows

The selected test ship is the only ship that may receive GUNPIRE orders.

Limit to one committed delivery for the test, then restore.

Use real production functions, not a separate fake delivery implementation.

Profile 2: TEST_DISPATCHER

Purpose: Validate demand calculation and scheduling without changing real ship orders.

Enable:

- Construction demand discovery
- Supplier evaluation
- Ship eligibility inspection
- Dispatch scoring
- Priority calculations
- Reservation simulation
- Full decision tracing

Disable:

- Real ship takeover
- Real purchase orders
- Real deliveries
- Modification of production reservation records
- Behavior restoration actions that are unnecessary because nothing was borrowed

Use isolated simulation state or read-only planning.

No physical game-economy changes are allowed.

Profile 3: TEST_FLEET

Purpose: Test real multi-ship coordination and dynamic resource allocation.

Enable:

- Approved test fleet only
- Shared dispatcher
- Multiple sites
- Dynamic scheduling
- Real deliveries
- Reservation reconciliation
- Priority weighting
- Safe restoration
- Full diagnostics

Do not automatically enroll unrelated player ships.

Profile 4: TEST_UI

Purpose: Validate native UI and MD/Lua communication.

Enable:

- Native UI
- Configuration controls
- Fleet and site display
- Status reporting
- UI event diagnostics
- Read-only game-state inspection where needed

Disable:

- Real ship takeover
- Autonomous dispatcher execution
- Trade execution

Use explicitly identified test data only where live data is unavailable.

Do not pretend simulated UI data represents game state.

Profile 5: FULL

Purpose: Enable the complete approved production system.

Enable:

- All approved construction logistics features
- All enrolled eligible ships
- Active and Passive operating functionality where supported by the approved scope
- Dynamic fleet allocation
- Full reservation tracking
- Native UI
- Recovery and restoration
- Normal operational diagnostics

FULL must not enable experimental or unfinished behavior.

A feature with an unresolved critical safety dependency must remain blocked even under FULL.
